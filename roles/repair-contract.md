For a technical package repair, include one authoritative `contract`: {objective, why_executable, prerequisites: [{id, status: verified|unresolved, reason, evidence: [zero-based indexes into report.evidence]}], requires: [prerequisite IDs], resolves: [prerequisite IDs], criteria: [{id, expectation, check: focused command}]}.
Explain why the step is executable without assuming the failed predecessor's missing proof. Requires may contain only verified prerequisites; resolves identifies what this step establishes, never what it assumes. Retain unresolved prerequisite IDs across reviews; verify them with evidence before marking them verified. Use an empty prerequisites list only when none exist. A new observation alone does not establish feasibility. If the implementation is blocked, commission the smallest independently executable prerequisite instead, not the blocked implementation again. Actual external prerequisites still use the existing owner-question protocol.
Put every required safety condition and completion check in the contract; keep next_action consistent with it. Do not duplicate the whole investigation: reference existing evidence. Assess the previous step against its own criteria separately from unfinished package requirements. A verified step_complete is progress, not another failed package repair.
