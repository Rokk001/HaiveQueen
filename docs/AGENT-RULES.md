# Agent rules

Project rules remain binding. The Queen receives the project work rules and, during integration, its integration rules. A Bee receives the complete project rules, never the whole plan.

## 1. Hard rules (tool)

1. One Hive works one plan with exactly one Queen at a time. The Queen coordinates and never works a package herself: every package goes to a Bee, respecting dependencies and the configured Bee limit. She also answers technical questions, merges the Bee branches locally and, when every requirement is done, integrates (git, compile check, build). Independent packages share no files.
2. A Bee receives only its package, numbered steps and needed paths, plus the complete project rules. It reports each finished step as `<Bee> <package>: step n/m <short text>` with `bzz note`. A code-changing Bee uses its own worktree and sub-branch; the Queen merges it locally.
3. Provider slots count Queens and Bees running as separate processes, not embedded subagents. The Beekeeper consumes no slot. Check free RAM before starting a Queen or separate Bee. Pause starts neither, and running Queens and embedded subagents continue.
4. Each package class is binding: the Bee gets the class of its package. The provider setting `beeMode` decides how the Bees of that provider's Queen run: as embedded `subagent`s (default for Claude) or as separate `process` agents (default for Codex). The local provider is used when available and suitable. A package requiring a capability goes to a provider offering it; if none is configured, ask the owner once. If the highest offered class for that capability fails the configured number of times, ask the owner. Excluded providers are never used.
5. Record failed attempts per package and class; interruptions do not count. After `escalateAfter` failed attempts, use the next higher offered class, resetting the count. If no higher class can solve it, ask the owner. Incompleteness alone does not escalate. If the Hive and local providers offer neither the required nor a higher class for a normal package, use another configured provider.
6. Before integrating, the Queen answers: “Were all tasks in the plan implemented? Are there any requirements that were not implemented?” Every requirement of the plan needs an id (section Requirements, lines `- <id>: <text>`; a plan without ids is refused). The Queen writes the answer into the state file beside the plan, in the section `## Completeness`, one line per requirement id, each id exactly once: `- <id>: done | <evidence>` (evidence is a file, commit or test). Status open or partial (German input such as teilweise is still read), a missing id or a missing evidence counts as open. Requirements covered exclusively by packages marked verify = "owner" when the plan was cut (HaiveQueen records the cut when `bzz plan check` accepts it or the owner starts a draft, and records an older READY plan when it is first read before any Queen or Bee of it started; the record belongs to one plan generation and its plan title, so edits of the plan text keep it while requirements added after the cut need evidence; another plan title at the path, a finished plan path used again, or a rejected or redrafted plan needs a new record, and without one evidence is required) and points the owner set aside in an active decision that names the id are listed separately and do not block. `bzz ready` of a Queen is decided only by this list and by a fresh check agent (class medium, provider chosen like a Bee's, loads like a Bee, took no part in the plan; role file roles/ready-check.md) that compares the plan as submitted with the list and the branch: only its result `READY-CHECK: PASSED` accepts the branch, `READY-CHECK: FAILED` returns the missing points to the Queen, and if the check agent cannot run `bzz ready` waits and runs again next round. The count line `Open requirements: <n>` is not read for a Queen's `bzz ready`; it stays for the verify phases of the old loop. Bees report their package result with evidence per requirement id they cover, so the Queen can copy it into the list.
7. Merge the current integration branch into the plan branch, retain both sides of conflicts, run the project check until successful and register the branch. Acquire the project's integration place and execute its integration rules for this Hive's own branch. A waiting Hive hands off; on acquiring the place abort an unfinished merge at the project integration checkout and retry. External windows acquire the same place using their stable owner process ID.
8. At the configured context limit, start no Bees, let running Bees finish, finish and commit the current step, write a handoff and end. A successor resumes in the same Hive. An unanswered owner question pauses only its item; work independent items first, then hand off until an answer arrives. A provider limit rests the Hive until reset without switching providers.
9. Plan statuses: DRAFT -> SENT -> PREPARING -> QUEUED -> RUNNING <-> WAITING -> REVIEW -> DONE, plus PAUSED and CANCELLED. SENT, PREPARING, QUEUED, RUNNING, WAITING and REVIEW plans get a Queen; packages start only in QUEUED, RUNNING, WAITING and REVIEW plans. The Beekeeper sets PREPARING when a Queen starts cutting a sent plan, QUEUED after a good cut, RUNNING while a Queen or Bee works, WAITING while every open package waits, REVIEW while the integrated plan waits for the owner check and DONE after it; only the owner sets PAUSED and CANCELLED. Old names (SUBMITTED, READY, IN_PROGRESS, REJECTED) are read as SENT, QUEUED, RUNNING and CANCELLED. The plan status is read from its TOML header or legacy status line.
10. Token economy is the first quality goal; context conservation is second. Give Bees only the material they need. A Queen whose provider cannot start subagents uses `beeMode = "process"`: every Bee is then a separate process.
