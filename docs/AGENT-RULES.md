# Agent rules

Project rules remain binding: the checked-in AGENTS.md and CLAUDE.md of the repository (and of the upstream repository when the project switched that on), the same for every agent of every phase. "Complete project rules" means all switched-on rule files: the Knowledge base section of the project page lists each file with its path and size in tokens and a switch; a switched-off file is given to no agent (a file a CLI loads itself from its folder, for example CLAUDE.md for Claude Code, stays switchable for the other CLIs and its line names the CLI that still loads it). The upstream rules come from the folder of the setting `upstreamRepo` (switch on) or, with the switch on, from the Git remote named upstream at its last fetch; the folder wins over the remote. The Queen receives the project work rules and, during integration, its integration rules. An Agent receives the complete project rules, never the whole plan.

## 1. Hard rules (tool)

1. One Plan works one plan with exactly one Queen at a time. The Queen coordinates and never works a package herself: every package goes to an Agent, respecting dependencies and the configured Agent limit. She also answers technical questions, merges the Agent branches locally and, when every requirement is done, writes the completeness answer, calls `bzz ready` and ends; she never integrates. Independent packages share no files.
2. An Agent receives only its package, numbered steps and needed paths, plus the complete project rules. It reports each finished step as `<Agent> <package>: step n/m <short text>` with `bzz note`. A code-changing Agent uses its own worktree and sub-branch; the Queen merges it locally.
3. Provider slots count every running Queen and Agent on the provider it runs on, including embedded subagents, which hold a slot until HaiveQueen closes their end. A subagent Agent uses a suitable local provider first, otherwise its Queen’s provider, otherwise another provider. A process Agent is placed on a suitable provider with the best quota reserve. A Queen needs one free slot; Agents wait when no suitable provider has a free slot. Every new Queen of an existing Plan chooses her provider by the normal provider choice unless the owner restarted her on a chosen provider; a running Queen is never moved. The Orchestrator consumes no slot. Check free RAM before starting a Queen or separate Agent. Pause starts neither, and running Queens and embedded subagents continue.
4. Each package class is binding: the Agent gets the class of its package. The provider setting `beeMode` decides how the Agents of that provider's Queen run: as embedded `subagent`s (default for Claude) or as separate `process` agents (default for Codex). The local provider is used when available and suitable. A package requiring a capability goes to a provider offering it; if none is configured, ask the owner once. If the highest offered class for that capability fails the configured number of times, ask the owner. Excluded providers are never used.
5. Record failed attempts per package and class; interruptions do not count. After `escalateAfter` failed attempts, use the next higher offered class, resetting the count. If no higher class can solve it, ask the owner. Incompleteness alone does not escalate. If the Plan and local providers offer neither the required nor a higher class for a normal package, use another configured provider.
6. Before integrating, the Queen answers: “Were all tasks in the plan implemented? Are there any requirements that were not implemented?” Every requirement of the plan needs an id (section Requirements, lines `- <id>: <text>`; a plan without ids is refused). The Queen writes the answer into the state file beside the plan, in the section `## Completeness`, one line per requirement id, each id exactly once: `- <id>: done | <evidence>` (evidence is a file, commit or test). Status open or partial (German input such as teilweise is still read), a missing id or a missing evidence counts as open. Requirements covered exclusively by packages marked verify = "owner" when the plan was cut (HaiveQueen records the cut when `bzz plan check` accepts it or the owner starts a draft, and records an older READY plan when it is first read before any Queen or Agent of it started; the record belongs to one plan generation and its plan title, so edits of the plan text keep it while requirements added after the cut need evidence; another plan title at the path, a finished plan path used again, or a rejected or redrafted plan needs a new record, and without one evidence is required) and points the owner set aside in an active decision that names the id are listed separately and do not block. `bzz ready` of a Queen is decided only by this list and by a fresh check agent (class medium, provider chosen like an Agent's, loads like an Agent, took no part in the plan; role file roles/ready-check.md) that compares the plan as submitted with the list and the branch: its result `READY-CHECK: PASSED` accepts the branch, or the owner explicitly releases it with `bzz plan release --project X --plan Y [--commit C]` (the legacy inbox decision with item `owner-release` remains valid); `READY-CHECK: FAILED` returns the missing points to the Queen, and if the check agent cannot run `bzz ready` waits and runs again next round. The count line `Open requirements: <n>` is not read for a Queen's `bzz ready`; it stays for the verify phases of the old loop. Agents report their package result with evidence per requirement id they cover, so the Queen can copy it into the list.
7. The Queen works until `bzz ready` and never integrates. After an accepted `bzz ready` the Orchestrator of HaiveQueen (no model) integrates the plan in the plan's worktree: Merge (the integration branch into the plan branch, both sides of conflicts retained), Check (the project's Compile check command), Build (Build command), Push (never forced) and Deploy (Deploy command); an empty command skips its step. A red step, or an owner rejection, starts a fix agent that works in the plan's worktree; the pipeline then starts again at Merge. One plan per project integrates at a time; a waiting plan resumes when its turn comes.
8. At the configured context limit, start no Agents, let running Agents finish, finish and commit the current step, write a handoff and end. A successor resumes in the same Plan. An unanswered owner question pauses only its item; work independent items first, then hand off until an answer arrives. Quota reserve is weekly quota multiplied by 5-hour quota (capped at 1), each quota being unused fraction divided by time remaining fraction; zero blocks that provider until reset. The Plan continues with available providers.
9. Plan statuses: DRAFT -> SENT -> PREPARING -> QUEUED -> RUNNING <-> WAITING -> REVIEW -> DONE, plus PAUSED and CANCELLED. SENT, PREPARING, QUEUED, RUNNING, WAITING and REVIEW plans get a Queen; packages start only in QUEUED, RUNNING, WAITING and REVIEW plans. The Orchestrator sets PREPARING when a Queen starts cutting a sent plan, QUEUED after a good cut, RUNNING while a Queen or Agent works, WAITING while every open package waits, REVIEW while the integrated plan waits for the owner check and DONE after it; only the owner sets PAUSED and CANCELLED. Old names (SUBMITTED, READY, IN_PROGRESS, REJECTED) are read as SENT, QUEUED, RUNNING and CANCELLED. The plan status is read from its TOML header or legacy status line.
10. Token economy is the first quality goal; context conservation is second. Give Agents only the material they need. A Queen whose provider cannot start subagents uses `beeMode = "process"`: every Agent is then a separate process.

HaiveQueen creates or reuses the package worktree at Agent start. Its branch is `<plan branch>-<package id in lower case>`; its folder is `<worktree prefix>-<plan tag in lower case>-<package id in lower case>`. The start answer gives both, including for subagents. An Agent never creates or commits on another branch.
## Plans with nothing left to integrate

A plan that changes no tracked file of the code repo has no plan branch and no queue row on purpose; a plan whose branch is already fully in the integration branch has nothing left to integrate either. Such a plan closes the same way as an integrated one, without integration: the Queen reports with `bzz ready` (no new queue row, no compile check, no Build or Deploy step) and ends. A fresh check agent passes the report, then the owner check asks to check the result of the plan (unless the plan header says `owner_check = "none"`), and acceptance sets DONE. No "queen-ended" question is filed. A failed check or a rejection sends the plan back to a new Queen with the open points.
