# Agent rules

Project rules remain binding. The Queen receives the project work rules and, during integration, its integration rules. A Bee receives only the rules needed for its package, not the full project instructions.

## 1. Hard rules (tool)

1. One Hive works one plan with exactly one Queen at a time. The Queen works packages herself and uses Bees for independent work, respecting dependencies and the configured Bee limit. Independent packages share no files; work under the Blender lock remains sequential.
2. A Bee receives only its package, numbered steps, needed paths and rules. It reports each finished step as `<Bee> <package>: step n/m <short text>` with `bzz note`. A code-changing Bee uses its own worktree and sub-branch; the Queen merges it locally.
3. Provider slots count Queens and Bees running as separate processes, not embedded subagents. The Beekeeper consumes no slot. Check free RAM before starting a Queen or separate Bee. Pause starts neither; drain lets running Queens finish, and embedded subagents continue.
4. Each package class is binding. The Queen works her class or lower herself; a higher class requires a Bee. For parallel work she works one package and delegates independent others. The local provider is used when available and suitable. Image packages use Codex; they wait when its slot or limit is unavailable. If no image provider is configured, ask the owner once. If Codex's highest offered class fails the configured number of times, ask the owner. Excluded providers are never used.
5. Record failed attempts per package and class; interruptions do not count. After `escalateAfter` failed attempts, use the next higher offered class, resetting the count. If no higher class can solve it, ask the owner. Incompleteness alone does not escalate. If the Hive and local providers offer neither the required nor a higher class for a normal package, use another configured provider.
6. Before integrating, the Queen answers: “Wurden alle Tasks aus dem Plan umgesetzt? Gibt es Anforderungen, welche nicht umgesetzt wurden?” List every requirement with evidence in the state file and end with `Offene Anforderungen: <n>`. Partial items count as open. Owner-only play checks are listed separately; the Queen integrates only with zero open requirements.
7. Merge the current integration branch into the plan branch, retain both sides of conflicts, run the project check until successful and register the branch. Acquire the project's integration place and execute its integration rules for this Hive's own branch. A waiting Hive hands off; on acquiring the place abort an unfinished merge at the project integration checkout and retry. External windows acquire the same place using their stable owner process ID.
8. At the configured context limit, start no Bees, let running Bees finish, finish and commit the current step, write a handoff and end. A successor resumes in the same Hive. An unanswered owner question pauses only its item; work independent items first, then hand off until an answer arrives. A provider limit rests the Hive until reset without switching providers.
9. READY and IN_PROGRESS plans can start. The Beekeeper sets IN_PROGRESS at Hive start and DONE after integration; only the owner or the one-time migration sets PAUSED. The plan status is read from its TOML header or legacy status line.
10. Token economy is the first quality goal; context conservation is second. Give Bees only the material they need. A Codex Queen without subagents works her own-class packages sequentially; higher classes and escalations use separate Bee processes.
